## 2. Why must we store passwords securely?

Imagine that you are developing a website where users can register and log in.

A user creates an account with the password:

```
MySecretPassword123
```

Your application needs to verify this password whenever the user logs in. But should you store the original password directly in your database?

No. You should never store users' passwords in plain text.

Suppose your database contains the following records:

| User  | Email                                         | Password            |
| ----- | --------------------------------------------- | ------------------- |
| Ali   | [ali@example.com](mailto:ali@example.com)     | MySecretPassword123 |
| Ahmed | [ahmed@example.com](mailto:ahmed@example.com) | Ahmed@123           |
| Sara  | [sara@example.com](mailto:sara@example.com)   | Sara@456            |

If a hacker gains access to this database, they can immediately read every password.

This is dangerous for two reasons:

1. The hacker can access users' accounts on your website.

2. If users reuse the same password on other platforms, the hacker may try it on their email, social media, banking, or other accounts.

### The correct approach

Instead of storing the original password, store a password hash generated by a password-hashing algorithm.

User enters password

`MySecretPassword123`

bcrypt hashes the password

Database stores the hash

Not the original password

Important: Hashing does not make a password impossible to guess. It makes recovering the original password computationally difficult, especially when a strong password and a suitable password-hashing algorithm are used.

## 3. Encryption: converting information into a protected form

### What is encryption?

Encryption is the process of converting readable information, called plaintext, into an unreadable form, called ciphertext, using an encryption algorithm and a key.

For example:

```
Original message + Encryption key
               |
               v
          Encryption
               |
               v
         Ciphertext
```

The person who possesses the appropriate decryption key can reverse the process and recover the original information.

### How does encryption work?

Suppose your application encrypts a piece of sensitive information.

1. The application receives the original information.

2. An encryption algorithm uses a key to encrypt it.

3. The application stores the ciphertext in the database.

4. When the original information is needed, authorized code decrypts it using the appropriate key.

### What is the problem with using encryption for passwords?

Encryption is designed to be reversible.

If a hacker obtains both the encrypted data and the decryption key, they may be able to recover the original information.

```
Original password
       |
       | Encrypt with key
       v
Encrypted password
       |
       | Decrypt with key
       v
Original password
```

If the decryption key is compromised, the protection may fail.

The key distinction: Encryption is useful when an application needs to recover the original data. Password verification normally does not require recovering the original password.

For example, an application may need to decrypt a stored API credential to use it. However, it should not need to decrypt a user's login password just to verify a login attempt.

## 4. Hashing: a one-way transformation

### What is hashing?

Hashing is the process of taking input data of any supported length and processing it through a hash function to produce a fixed-length digest for a given algorithm.

For password storage, we use a specialized password-hashing algorithm rather than a fast general-purpose hash such as MD5 or plain SHA-256.

Example:

```
Input:  MySecretPassword123
              |
              v
      Password hash function
              |
              v
Output: $2b$10$... (bcrypt hash)
```

The hash is not intended to be decrypted.

### Encryption vs. hashing

| Feature          | Encryption                                 | Hashing                                                                     |
| ---------------- | ------------------------------------------ | --------------------------------------------------------------------------- |
| Main purpose     | Protect data that may need to be recovered | Verify data without storing the original                                    |
| Reversible?      | Yes, with the appropriate key              | Not designed to be reversed                                                 |
| Uses a key?      | Normally uses an encryption key            | Password hashing uses algorithm parameters and a salt, not a decryption key |
| Password storage | Not the usual choice                       | The appropriate approach                                                    |
| Example          | AES                                        | bcrypt, Argon2id, scrypt                                                    |

### Understanding the one-way property

Your lecture expresses the idea as:

```
Original password  →  Password hash
Password hash      ↛  Direct decryption to original
```

The second arrow is not a normal decryption operation. However, a hacker can still try candidate passwords, hash them using the same parameters, and compare the results.

For example:

```
Candidate: password123
       |
       v
Run bcrypt with the stored salt and cost
       |
       v
Compare with the stored hash
       |
       +---- Match? ----> Candidate is correct
```

This is why hashing alone is not the whole solution. We also need a suitable algorithm, unique salts, an appropriate work factor, and strong user passwords.

## 5. How do hackers crack password hashes?

A hacker does not need to decrypt a hash. They can attempt to guess the original password.

There are several common approaches.

### A. Brute-force attack

The attacker tries many possible passwords.

```
123456
password
password123
MySecretPassword123
       ...
```

If a candidate produces a matching password hash, the attacker has found the password.

### B. Dictionary attack

Instead of trying every possible combination, the attacker tries likely passwords from a prepared list.

Common choices include:

- `123456`

- `password`

- `qwerty`

- Names and birthdays

- Common words and predictable variations

A strong, unique password makes these attacks harder.

### C. Rainbow tables

A rainbow table is a precomputed structure that helps attackers look up or reverse certain password-hash mappings efficiently.

For example, imagine an attacker has a lookup table containing:

| Candidate password | Precomputed hash |
| ------------------ | ---------------- |
| `apple123`         | `hash_A`         |
| `hello123`         | `hash_B`         |
| `password123`      | `hash_C`         |

If the stolen database contains a matching hash, the attacker may identify the password without computing every guess from scratch.

This approach is particularly effective against common passwords stored with fast, unsalted hash functions.

Correction to the lecture: Rainbow tables do not work by assigning a code to each letter, such as `a = 123` and `b = 234`. They rely on precomputed relationships between candidate inputs and hash outputs. Also, bcrypt is not immune to cracking; it makes each password guess deliberately expensive.

## 6. Salting: adding uniqueness to password hashing

Now consider a problem.

Two users register with the same password:

```
Ali's password:   hello123
Ahmed's password: hello123
```

With a deterministic hash function and no salt, the same password produces the same hash.

```
hello123 → hash_A
hello123 → hash_A
```

An attacker who discovers that the hashes match can infer that the two users have the same password. Precomputed attacks may also become much more effective.

### What is a salt?

A salt is a randomly generated value used by a password-hashing algorithm when generating a password hash.

Conceptually:

```
Password + Salt
       |
       v
Password-hashing algorithm
       |
       v
Password hash
```

For example:

```
Ali:
Password = hello123
Salt     = salt_A
Hash     = hash_A

Ahmed:
Password = hello123
Salt     = salt_B
Hash     = hash_B
```

Because the salts differ, the resulting hashes differ, even though both users chose the same password.

These are simplified examples, not actual bcrypt output.

### Why does salting help?

1. It prevents identical passwords from automatically producing identical stored hashes when different salts are used.

2. It makes precomputed rainbow tables for unsalted passwords ineffective against the salted values.

3. It forces an attacker to perform password guesses separately for each salt and hash.

A salt does not make a weak password strong, and it does not need to be secret.

## 7. Should every user have the same salt or a different salt?

This is an important design decision.

### Method A: One shared salt

```
Ali's password   + Shared salt → Hash A
Ahmed's password + Shared salt → Hash B
Sara's password  + Shared salt → Hash C
```

The salt could be stored in server configuration, but it would be shared by all users.

Problem: If the shared salt becomes known, it does not provide per-user uniqueness. Passwords that are the same will still produce the same hash under this arrangement.

### Method B: A unique salt for every password

```
Ali's password   + Salt A → Hash A
Ahmed's password + Salt B → Hash B
Sara's password  + Salt C → Hash C
```

Advantage: Each password hash has its own salt. An attacker cannot reuse a single precomputed table to efficiently attack all the users' hashes.

Recommended

### But do we have to store every salt in the database?

Yes, the salt must be available when verifying a password. However, you do not need to create a separate database field or manage it manually when using bcrypt correctly.

bcrypt stores the salt and algorithm parameters inside the resulting hash string. When you save that hash, you save the information required for later verification as well.

## 8. What is bcrypt?

bcrypt is a password-hashing algorithm designed to make password guessing computationally expensive.

It provides three important features:

- Salt generation: Generates a random salt for the password hash.

- Work factor: Controls how computationally expensive the hashing process is.

- Verification: Compares a candidate password against a stored hash without decrypting it.

For a new application, Argon2id is generally the preferred option where available. bcrypt remains useful for learning and for systems that use it, provided it is configured appropriately.

## 9. Understanding the bcrypt code, line by line

Here is the original lecture code, with explanations added.

JavaScript

```
const bcrypt = require("bcrypt");

const password = "Your password";

async function hashPass() {
  const salt = await bcrypt.genSalt(10);

  const hashed = await bcrypt.hash(password, salt);

  // Compare the entered password with the hash
  const ans = await bcrypt.compare(password, hashed);

  console.log(ans);

  // console.log(hashed);
  // console.log(salt);
}

hashPass();
```

### Line 1: Import bcrypt

JavaScript

```
const bcrypt = require("bcrypt");
```

This loads the bcrypt library so the program can use its password-hashing functions.

### Line 2: Define the password

JavaScript

```
const password = "Your password";
```

This is the original password entered by the user in this demonstration.

In a real application, the password would normally come from validated request data, such as `req.body.password`, rather than being hardcoded.

### Line 3: Define an asynchronous function

JavaScript

```
async function hashPass() {
```

The `async` keyword allows the function to use `await`.

Password hashing takes time, and bcrypt's asynchronous functions allow the program to wait for their results without blocking the Node.js event loop in the same way a synchronous bcrypt call would.

### Line 4: Generate a salt

JavaScript

```
const salt = await bcrypt.genSalt(10);
```

This line deserves special attention.

- `bcrypt.genSalt()` generates a random salt and encodes the selected cost factor.

- `10` is the work factor, also called the cost parameter.

- `await` waits for the salt-generation promise to resolve.

- `const salt` stores the generated salt string.

Why `10`?

In bcrypt, the cost parameter is exponential: a cost of 101010 corresponds to a work factor proportional to 2102^{10}210, while a cost of 111111 approximately doubles the computational work.

It does not mean ten rounds in the ordinary sense of ten repetitions.

Higher costs make password hashing and verification slower, increasing the expense of trying password guesses. Choose a cost that balances security with the response time and capacity of your server. A cost of 10 is a common minimum baseline, not a universal ideal for every application.

### Line 5: Hash the password

JavaScript

```
const hashed = await bcrypt.hash(password, salt);
```

This line takes the original password and the generated salt and produces a bcrypt hash.

Step by step:

1. `password` is the original password.

2. `salt` contains the generated salt and cost information.

3. `bcrypt.hash()` processes the password using bcrypt.

4. `await` waits for the result.

5. `hashed` contains the resulting hash string.

The resulting value is what you store in the database.

Important: Never replace the database's stored password hash with the original password.

### Line 6: Compare the password

JavaScript

```
const ans = await bcrypt.compare(password, hashed);
```

This checks whether the candidate password matches the password represented by the stored bcrypt hash.

The library extracts the salt and cost information from the stored hash, processes the candidate password, and checks the result.

- If the password matches, the function resolves to `true`.

- If the password does not match, it resolves to `false`.

It does not decrypt the hash.

### Line 7: Display the result

JavaScript

```
console.log(ans);
```

Since the demonstration compares the same password used to create the hash, the output is:

```
true
```

If you compare a different password, the result will be `false`.

### Line 8: Call the function

JavaScript

```

```

Defining a function does not execute its body. Calling `hashPass()` starts the process.

For a real application, you should also handle errors with `try...catch` and await the operation where appropriate.

## 10. How to read a bcrypt hash code

Your lecture provides this example:

```
$2b$10$tXCdbqYVEDChUFIiI/Kr0OvI08Nyu7VgkKaHfianWmweFPAVJzccq
```

A bcrypt hash has a structured format. It is not just a random string.

## Anatomy of a bcrypt hash

VERSION

# $2b$

Identifies the bcrypt version.

COST FACTOR

# 10

Controls the computational work, approximately proportional to 210=10242^{10}=1024210=1024.

SALT

## 22 characters

Encodes the random salt used to hash the password.

HASH DIGEST

## 31 characters

Contains the encoded password-derived hash result.

The standard bcrypt modular string is normally 60 characters long. Its structure is:

```
$2b$10$[22-character salt][31-character digest]
```

The dollar signs (`$`) separate the version and cost fields. The salt and digest follow one another without another separator.

The version is `2b`, the cost is `10`, and the remainder contains the salt and digest.

## 11. A more practical bcrypt example

Let's improve the original example by checking both a correct and an incorrect password.

JavaScript

```
const bcrypt = require("bcrypt");

async function hashPass() {
  try {
    const password = "MyStrongPassword123";

    // 1. Generate a random salt
    const salt = await bcrypt.genSalt(10);

    // 2. Hash the password
    const hashed = await bcrypt.hash(password, salt);

    console.log("Stored hash:", hashed);

    // 3. Test the correct password
    const correct = await bcrypt.compare(
      "MyStrongPassword123",
      hashed
    );

    console.log("Correct password:", correct);

    // 4. Test an incorrect password
    const incorrect = await bcrypt.compare(
      "WrongPassword123",
      hashed
    );

    console.log("Incorrect password:", incorrect);
  } catch (error) {
    console.error("Password operation failed:", error);
  }
}

hashPass();
```

Expected output:

```
Stored hash: $2b$10$... (actual generated hash)
Correct password: true
Incorrect password: false
```

The actual hash will differ between runs because bcrypt generates a new random salt.

### Why is the output different every time?

Suppose you hash the same password twice:

JavaScript

```
const hash1 = await bcrypt.hash("hello123", 10);
const hash2 = await bcrypt.hash("hello123", 10);
```

Both hashes should be different because bcrypt uses a random salt.

Yet both comparisons should succeed:

JavaScript

```
await bcrypt.compare("hello123", hash1); // true
await bcrypt.compare("hello123", hash2); // true
```

This demonstrates why you must not verify a password by comparing a newly generated hash directly with the stored hash.

Use `bcrypt.compare()` instead.

## 12. How password hashing works in a real application

The previous code demonstrates bcrypt, but a real application must handle two separate processes: registration and login.

## Registration flow

1. The user submits their email and password.

2. The server validates the request and password requirements.

3. The server hashes the password using bcrypt.

4. The server saves the email and hash in the database.

5. The original password is not stored.

## Login flow

1. The user submits their email and password.

2. The server finds the user's record using the email.

3. The server retrieves the stored password hash.

4. `bcrypt.compare()` checks the submitted password against the stored hash.

5. If the password matches, the server continues authentication; otherwise, it rejects the login.

### Example database record

A MongoDB user document might look like this:

JavaScript

```
{
  email: "ali@example.com",
  password: "$2b$10$..."
}
```

Here, `password` contains the bcrypt hash, not the original password.

You normally do not need separate `salt` and `cost` fields because bcrypt encodes that information in the stored hash.

## 13. A complete registration and login example using Express

This example demonstrates the core password logic. It assumes that you already have an Express application and a MongoDB/Mongoose `User` model.

### Registration

JavaScript

```
const bcrypt = require("bcrypt");

app.post("/register", async (req, res) => {
  try {
    const { email, password } = req.body;

    if (
      typeof email !== "string" ||
      typeof password !== "string" ||
      !email.trim() ||
      !password
    ) {
      return res.status(400).json({
        message: "Email and password are required",
      });
    }

    const existingUser = await User.findOne({
      email: email.trim().toLowerCase(),
    });

    if (existingUser) {
      return res.status(409).json({
        message: "Unable to register with this email",
      });
    }

    const hashedPassword = await bcrypt.hash(password, 10);

    const user = await User.create({
      email: email.trim().toLowerCase(),
      password: hashedPassword,
    });

    return res.status(201).json({
      message: "Registration successful",
      userId: user._id,
    });
  } catch (error) {
    console.error("Registration failed:", error);

    return res.status(500).json({
      message: "An internal error occurred",
    });
  }
});
```

Understand the important line:

JavaScript

```
const hashedPassword = await bcrypt.hash(password, 10);
```

This creates a salted bcrypt hash using cost factor 10. The database receives the hash rather than the original password.

The example is illustrative. A production system should also enforce password policy, apply request rate limits, and enforce email uniqueness with a database index to prevent concurrent duplicate registrations.

### Login

JavaScript

```
app.post("/login", async (req, res) => {
  try {
    const { email, password } = req.body;

    if (
      typeof email !== "string" ||
      typeof password !== "string"
    ) {
      return res.status(400).json({
        message: "Invalid request",
      });
    }

    const user = await User.findOne({
      email: email.trim().toLowerCase(),
    });

    if (!user) {
      return res.status(401).json({
        message: "Invalid email or password",
      });
    }

    const isMatch = await bcrypt.compare(
      password,
      user.password
    );

    if (!isMatch) {
      return res.status(401).json({
        message: "Invalid email or password",
      });
    }

    // Continue with your application's
    // session or token creation here.

    return res.status(200).json({
      message: "Login successful",
    });
  } catch (error) {
    console.error("Login failed:", error);

    return res.status(500).json({
      message: "An internal error occurred",
    });
  }
});
```

Notice that the login code does not create a new hash and compare the two strings. It passes the entered password and the stored hash to `bcrypt.compare()`.

Also, a successful password comparison is not the end of the authentication process. A real application must establish a secure session or issue an appropriate authentication token.

## 14. Important security rules to remember

- Never store plaintext passwords. Store a suitable password hash.

- Never encrypt passwords just so you can decrypt them during login. Password verification does not require recovering the original password.

- Use a unique random salt for every password hash. bcrypt generates and embeds it automatically.

- Do not use plain MD5 or SHA-256 for password storage. They are too fast for this purpose.

- Use a suitable work factor. Benchmark the setting on your actual server.

- Protect your database and application. Password hashing does not prevent SQL/NoSQL injection, account takeover, insecure sessions, or other vulnerabilities.

- Use HTTPS. Hashing in the database does not protect a password sent over an insecure network.

- Never log passwords. Avoid printing request bodies or credentials in production logs.

- Consider bcrypt's 72-byte input limit. If supporting long passwords, choose and implement a suitable strategy; do not casually pre-hash passwords without understanding the risks.

- Consider Argon2id for new applications. It is the preferred option in current OWASP guidance when available and appropriately configured.

## 15. Interview questions and answers

### Q1. Why should we hash passwords instead of encrypting them?

Because the application only needs to verify whether the entered password is correct. Hashing avoids keeping a reversible representation of the original password.

### Q2. Can we decrypt a bcrypt hash?

No. bcrypt is a one-way password-hashing algorithm. Attackers may guess passwords and test them against the hash, but there is no normal decryption operation.

### Q3. Why do we use salt?

A unique salt prevents identical passwords from producing identical bcrypt hashes and helps defeat precomputed rainbow-table attacks.

### Q4. Should we keep the salt secret?

No. The salt can be stored alongside the hash. Its purpose is uniqueness, not secrecy.

### Q5. Why does bcrypt produce different hashes for the same password?

Because it generates a new random salt for each hash operation.

### Q6. Why do we use `bcrypt.compare()`?

Because it verifies a candidate password against the stored hash using the salt and parameters encoded in that hash.

### Q7. What does `bcrypt.genSalt(10)` mean?

It generates a random salt using bcrypt's cost factor of 10. The work factor is exponential, approximately proportional to 2102^{10}210.

### Q8. What happens if a hacker steals the database?

The attacker obtains password hashes instead of plaintext passwords. They may still attempt offline guessing, so strong passwords and properly configured password hashing remain essential.

### Q9. What is the difference between salt and pepper?

A salt is unique to each password hash and is normally stored with it. A pepper is an additional secret shared across hashes and kept separately from the database.

### Q10. Should we hash a password again every time a user logs in?

No. On registration or password change, generate and store a new hash. On login, use `bcrypt.compare()` against the existing hash.
